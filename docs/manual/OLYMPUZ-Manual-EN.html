1. Introduction

Olympuz Coder is an AI coding agent (a fork of Claude Code) extended with three specialist departments that turn it from a single assistant into an on-demand organization. Each department is a self-contained "team" of purpose-built agents that share a common engine, inject their own Product Requirements Document (PRD) into the system prompt, plan work as a dependency graph, and curate reusable knowledge to a knowledge graph.

DepartmentDefaultWhat it does
STUDIO Design & GenerationEnabled Design systems & design-token generation for web, Android and Windows; brand-aligned UI/UX, design-token emission (CSS, Compose Kotlin, WinUI XAML).
OPS Agentic OperationsOpt-in Computer-use control of Windows & any browser; vision, speech-to-text (ears), text-to-speech (voice); autonomous agent teams with an org board.
MARKETING Marketing & GrowthEnabled Complete marketing campaigns: image / video / short-form generation, copywriting, official profiles, social-media publishing, send & receive email.
The unifying promise. Every department plans before it acts, asks a human before anything outward-facing or destructive, and logs what it publishes so it can be reviewed and reversed. You stay in control; the agents do the heavy lifting.

2. Installation & Requirements

2.1 System requirements

  • OS: Windows 11 (primary), macOS or Linux also work.
  • Node.js: 22+ (the SQLite knowledge-graph backend uses the built-in node:sqlite; Bun uses native bun:sqlite).
  • RAM: 6 GB minimum practical; the launcher auto-clamps the V8 heap to 55% of free RAM, range [768, 3072] MB, to avoid swap-thrash freezes on low-RAM boxes.
  • Disk: ~600 MB for dependencies + browser binaries if you use Ops.

2.2 Install & build

# from the repository root
npm install            # install dependencies
npm run build          # bun esbuild bundle → dist/cli.mjs
npm run smoke          # build + verify the binary boots (prints version)

# optional gates
npm run typecheck      # tsc --noEmit  (must report 0 errors)
npm test               # full vitest suite (~2639 pass | 0 fail | 7 skip)

2.3 Run it

# interactive TUI
node dist/cli.mjs

# one-shot prompt (headless)
node dist/cli.mjs -p "explain this repository"

# show version
node dist/cli.mjs --version          # → 1.0.0 (Olympuz Coder)

The olympuz launcher (bin/olympuz / olympuz.cmd on Windows) wraps dist/cli.mjs and sets the dynamic heap. Source-mode npm run dev exists but is not a supported production workflow — always run the built bundle.

3. Architecture — The Department Pattern

Every department is a sibling under src/<dept>/ and follows the same proven shape. A small shared core (src/departments/) wires them together.

3.1 Inside a department

ModuleResponsibility
types.tsConfig, intent, governance, role, plan, run-result types.
principles.tsThe department PRD (full + compressed). A versioned grounding document injected into the system prompt when active.
intent.tsDetects whether a user message is a request for this department, with a confidence score and triggers.
governance.tsPolicy resolution with the hierarchy Director > domain > default. Admin-settable keys per domain.
department.tsThe specialist org chart (roles + missions) and the planner that turns intent + governance into a dependency-ordered task graph.
curator.tsThe single module that touches the knowledge graph — extracts reusable assets after a run and persists them under a namespaced key.
<dept>Engine.tsLazy singleton: holds config + governance; exposes is<Dept>Active(), intent detection, planning, curator runner.
inject.tscompose<Dept>AppendSystemPrompt(existing) — appends the PRD when active, returns input unchanged when dormant.

3.2 The shared core (src/departments/)

FileResponsibility
inject.tscomposeAllDepartmentInjections(existing) stacks Studio + Ops + Marketing prompts in sequence. Each early-returns when inactive, so the stack is byte-identical to "before" when no department is active.
approval.tsbuildApprovalCheck / needsApproval(policy, destructive) — the gate primitive used by all outward-facing tools. Policies: allow, ask-destructive, ask-always.
publishedLog.tsAppend-only JSONL of everything published (Marketing). recordPublish, listPublishes, getPublish, markReversed.
Test-safety invariant. isTestEnv() is true under vitest (process.env.VITEST or NODE_ENV === 'test'). Every department is dormant under test regardless of config, so prompts, agent lists and tool lists stay byte-for-byte stable. The full suite of ~2639 tests is unaffected by the departments.

4. Studio — Design & Generation Department STUDIO

PRD v2026.07.05 · Default: enabled · Activation: auto-on for build intent.

Studio is the design department. On detecting design/build intent it produces a design system and emits concrete design tokens for three platforms from one source of truth, plus a delegation plan for the specialist roster.

4.1 Supported surfaces

  • Platforms: web, android, windows.
  • Aesthetics (moods): neutral-adaptive, luxury-dark-gold, calm, vibrant, minimal, bold.
  • Token outputs: CSS custom properties (web), Compose Kotlin (Color.kt/Type.kt/Shapes.kt, Android), WinUI XAML ThemeDictionaries (Windows).
  • Quality gates: WCAG contrast verification (contrastAA), semantic color roles (bg / fg / accent), a verified base color.

4.2 The /studio command

/studio                                  # help
/studio run <brief>                       # plan + tokens for a brief
/studio tokens [base] [mood] [--platform web|android|windows]
/studio principles                        # print the full Studio PRD
/studio admin list                        # show active governance
/studio admin get <domain> <key>            # resolve one policy
/studio admin set <domain>.<key>=<val>     # set a policy
/studio knowledge stats                   # knowledge-base counts
/studio knowledge recall <query>          # recall studio knowledge
/studio enable | disable                  # toggle the department
/studio status                            # current state

4.3 Example session

/studio run a calm fintech dashboard for web, luxury mood
/studio tokens #0b1f3a luxury-dark-gold --platform android

5. Ops — Agentic Operations Department OPS

PRD v2026.07.05 · Default: opt-in (disabled) · Activation: explicit /ops enable or OLYMPUZ_OPS_ENABLED.

Ops turns Olympuz into a computer-use agent. It controls Windows and any browser, sees the screen (vision), hears (STT), speaks (TTS), and can form autonomous agent teams coordinated through a native swarm runtime with an org board.

Ops is opt-in for safety. Real machine control is powerful and dangerous, so Ops is dormant until you explicitly turn it on. Destructive actions always ask for per-action approval (mouse/keyboard, shell, file-delete, browser submit/payment). Read-only actions — screenshot, the accessibility tree, vision, listen, speak, read-only browse — do not ask.

5.1 Surfaces

SurfaceCapability
computerWindows desktop control via PowerShell + .NET (System.Drawing screenshot, System.Windows.Forms cursor/keystroke, UIAutomation a11y tree).
browserDeterministic Playwright when selectors are known; vision-driven when not. Navigation confined to a governance allowlist.
visionScreenshot metrics + multimodal LLM judgment (describe, OCR, compare).
voiceSTT (streaming or batch; project keyterm boosting) and TTS (speak(): Windows SAPI / macOS say / Linux espeak / provider).
automationMulti-step plan: idempotent step graph, fail-safe, step budget (automation.maxSteps).
teamsAutonomous teammates via native swarm (TeamCreate, SendMessage, Agent). teams.requireApproval gates creation; teams.maxTeammates bounds size.

5.2 The /ops command

/ops team list                            # show autonomous-team capability
/ops team new <goal>                      # plan a team for a goal
/ops team spawn <role>                    # plan spawning one specialist
/ops review                               # recent ops knowledge + state

/ops knowledge stats | recall <query>

6. Marketing & Growth Department MARKETING

PRD v2026.07.06 · Default: enabled · Activation: auto-on for campaign/creative/social/email intent.

Marketing builds complete campaigns end-to-end: strategy, copy, on-brand visual creative, video and short-form generation, official profile creation, social-media publishing across five platforms, and full email lifecycle (send + receive).

The publish gate (non-negotiable). Every publish / send / post asks a human for approval before it goes out, and is then appended to the reversible published log. You can review everything published and reverse what isn't right: /marketing review, /marketing reverse <id>. Read actions (inbox) never ask.

6.1 Capabilities

  • Creative generation: images (ImageGen — DALL·E 3 / Stability / local), video & shorts (VideoGen — Veo 3 / Sora 2 / Runway Gen-5 / Kling 3).
  • Channels: X, Meta, LinkedIn, TikTok, YouTube (publish + delete); Email via SMTP + IMAP (send + inbox).
  • Compliance built in: email is permission-only, double opt-in, with a clear unsubscribe path.

7. Safety, Approval Gates & Kill Switches

Safety is structural, not advisory. Three independent mechanisms keep you in control.

7.1 The approval gate

Every outward-facing or destructive tool implements checkPermissions(input, context) which returns one of:

  • { behavior: 'allow', updatedInput } — proceeds.
  • { behavior: 'ask', message, updatedInput } — pauses and shows you exactly what it wants to do; you approve or deny.

The policy is resolved from governance with the hierarchy Director > domain > default:

PolicyBehavior
ask-alwaysAsks every time. Marketing's publish actions use this.
ask-destructiveAsks only for destructive actions. Ops' default for computer/browser control.
allowProceeds without asking. Not recommended for outward-facing actions.

7.2 The published log (Marketing)

Append-only JSONL at <CLAUDE_CONFIG_DIR>/marketing/published.jsonl. Every published item records: id, channel, action, target, content, timestamp, status, reversible, and a reversalHint. Reversal deletes/unlists the post and marks the entry reversed. (Email sends are generally not mechanically reversible — send a correction/follow-up instead.)

7.3 Kill switches (absolute)

Each department's OLYMPUZ_<DEPT>_ENABLED=false is a hard kill switch. It is checked first, before config and before the test force-active hatch. Setting it disables the department even if config says otherwise.

SwitchScope
OLYMPUZ_OPS_ENABLED=falseOps fully off — no PRD injection, no ops-* agents/tools, no machine control.
OLYMPUZ_MARKETING_ENABLED=falseMarketing fully off — no PRD injection, no marketing-* agents/tools, no publishing.
OLYMPUZ_COMPUTER_CONTROLGates the legacy ComputerControlTool (defense in depth).
OLYMPUZ_DEVICE_BRIDGEGates the ADB device bridge.

8. Configuration (settings.json)

Each department has an optional block in your settings schema. Settings are loaded from ~/.olympuz/settings.json (or the platform equivalent). The slash commands (/studio enable, etc.) mutate the in-memory config at runtime.

8.1 Studio

"studio": {
  "enabled": true,
  "autoActivate": true,
  "intensity": "ultra",                 // "standard" | "premium" | "ultra"
  "defaultPlatform": "web",             // "web" | "android" | "windows"
  "aesthetic": "neutral-adaptive"       // see moods in §4.1
}

8.2 Ops

"ops": {
  "enabled": false,                     // OPT-IN (defaults false)
  "autoActivate": false,
  "intensity": "standard",
  "surfaces": ["computer","browser","vision","voice","automation"],
  "approvalPolicy": "ask-destructive"   // "ask-destructive" | "ask-always" | "allow"
}

8.3 Marketing

"marketing": {
  "enabled": true,                      // mirrors Studio
  "autoActivate": true,
  "intensity": "ultra",
  "channels": [],                       // allowlist; empty = all
  "publish": {
    "approvalPolicy": "ask-always",     // recommended
    "logging": true                     // append to published log
  }
}

8.4 Governance directives

Set any policy from the chat with /<dept> admin set <domain>.<key>=<value>. For Director-level overrides use the director.<domain>.<key> form, which beats every other source. Booleans accept true/false; comma-separated values become lists only when a comma is present (a single value stays a string).

12. Knowledge Graph & the Curator

Each department's curator is the only module that writes to the knowledge graph. After a run it extracts reusable assets and persists them under a namespaced key, so departments never collide and lessons compound over time.

DepartmentEntity types
Studiostudio-* (design systems, token sets, brand assets)
Opsops-macro (recorded action sequences), ops-selector (winning selectors), ops-workflow
Marketingmarketing-campaign, marketing-creative (+prompt), marketing-copy, marketing-audience
Marketing publishmarketing-publish (one entity per published item — the audit trail)

Persistence uses node:sqlite under Node (22+) and bun:sqlite under Bun, behind a unified adapter. shutdownGlobalGraph() closes all cached provider handles — important on Windows to avoid EPERM on directory cleanup. Recall any department's knowledge with /<dept> knowledge recall <query>.

13. Workflows & Quick Start

13.1 Design a product (Studio)

/studio run a calm productivity app for Windows, minimal mood
# → tokens emitted for web + Android + Windows; delegation plan for the roster

13.2 Automate a desktop task (Ops)

/ops enable
/ops run open the browser, log the cheapest USB-C hub price to prices.csv
# → destructive steps (save file) ask approval; read-only steps (browse) do not

13.3 Ship a campaign (Marketing)

/marketing run launch Olympuz Coder on X and LinkedIn with one hero image
# → strategy + copy + creative + publish-ready items; each post asks before it goes live
/marketing review                  # audit everything published
/marketing reverse <id>            # undo a post that isn't right

13.4 Daily operations checklist

  1. /<dept> status — confirm the department you need is active.
  2. /<dept> run <brief> — review the plan before delegating.
  3. Approve outward-facing actions when prompted.
  4. /<dept> knowledge recall <query> — reuse prior learnings.
  5. For Marketing: /marketing review regularly; reverse anything wrong.

14. Troubleshooting

SymptomFix
Department seems inactiveRun /<dept> status. Check enabled and the kill switch env var. Ops requires explicit /ops enable.
"configure X" result from an adapterThe relevant credentials aren't set. Add the env vars (§6.4, §9) and restart.
Tool/agent absentDepartment tools/agents register only when active. Activate the department, then retry.
Freezes after several steps (low-RAM box)The launcher clamps the heap to [768, 3072] MB @ 55% free RAM. Close other apps; rerun olympuz so it recomputes free RAM.
Suite flakes under loadOn 6 GB boxes a few dynamic-import() tests can time out under memory pressure. They pass green in isolation; rerun the specific file.
EPERM on Windows cleanupKnowledge-graph handles left open across tests. shutdownGlobalGraph() closes them; ensure it's called in afterAll.
Source-mode npm run dev crashesNot a supported workflow. Always run the built dist/cli.mjs.
